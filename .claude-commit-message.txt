one line in an action file broke 252 routes

a11d0072 failed to build. Production never moved off 55590c25, so the shadow
day step shipped nowhere. One line of mine, in
src/lib/admissions/decisions.ts:

    export type { DecisionType };

    Export DecisionType doesn't exist in target module
    The export DecisionType was not found in module
      [project]/src/lib/admissions/decisions.ts [app-rsc] (ecmascript)

252 of them, one per route in the JAG, plus the comment I had written beside
the line: "It is a type, so it erases and does not become a server action."

WHY THAT SENTENCE IS FALSE

Next's server-actions transform reads the EXPORT NAMES of a "use server"
module and writes one action binding per name into every route's generated
actions.js - BEFORE TypeScript erases the types:

    export {DecisionType as '7fc922871dc64090...'} from 'ACTIONS_MODULE2'

The type then vanished, as types do, and 252 routes held a reference to an
export that was not there.

`export type Foo = ...` is fine, and twelve other "use server" files in the
JAG use it - a type DECLARATION is stripped whole before the transform runs.
It is the re-export SPECIFIER LIST, `export { X }` or `export type { X }`,
that the transform picks up by name. I did not know that distinction. I do
now, and so does the repository.

HOW IT GOT PAST EVERYTHING

The scoped typecheck was green. claude-ship.ps1's own typecheck was green.
Two hundred tests passed. tsc erases the type and is satisfied - there is
nothing for it to object to. A GREEN TYPECHECK IS NOT EVIDENCE OF A BUILD,
which is written down in this repository from 3 October and was learned again
here at the cost of one failed deploy and an hour.

HOW IT WAS FOUND

Not by guessing. The Vercel connector returns 403 on this project's build
logs, the CLI on the machine has no credentials, and `next build` cannot run
in the device shell - it wants a Linux SWC binary and has no npm access. So
the source was packaged, carried into a container with network, installed and
BUILT: 497 errors, 252 of them this one. Removing the line took it to 245, and
all 245 are `Can't resolve '@academyos'`-class aliases pointing at the root
packages/ folder the package deliberately left out. Which is to say: this line
was the only fault in the change.

THE GUARD

tests/unit/admissions/no-type-reexport-from-an-action.test.ts walks every
"use server" file in src/ and fails on any export specifier list, naming the
file and the line. It was checked both ways - it passes now, and with the line
put back it fails on decisions.ts:52.

It also asserts that the walker found more than five action files, because a
file walker that silently finds nothing passes every other assertion and
guards nothing; and that more than five of those files still use
`export type Foo = ...`, so the rule cannot quietly get greedy and send
somebody hunting a problem that is not there.

The reason is written into decisions.ts itself, above the imports, because the
next person will have the same good reason to re-export a type from that exact
file and the error they would get names a route they never touched.
