the guard could not name the door

Heather Badger-Brown, School Leader of The Academy HS, signed in at thejag.org
with the correct password and was told:

    Your password is correct, but this account is not part of The JAG™
    Platform. ... Use the link in the email your school sent you, or ask your
    school's admissions office for the sign-in address.

She is the school's admissions office.

That is the FALLBACK wording. The guard is built to name the address —
"Sign in here instead: <campus>.thejag.org/login" — and falls back only when it
cannot work out which campus somebody belongs to. It could never work it out.
The named-address path has never once run.

TWO IDENTITY NAMESPACES, NOTHING BETWEEN THEM

resolveTenantSignInHost reads schools.organization_id, a uuid, and hands it to
BrandRegistry.getByOrganizationId. The registry is keyed by SYNTHETIC TEXT IDS.
Migration 226 says so in its own header: "the registries use synthetic text ids
(org.the-academy-way)".

Production holds exactly one brand row:

    organization_id       subdomain   organization_name
    -------------------   ---------   -----------------
    org.the-academy-way   academy     The Academy Way

A uuid cannot match that key. Every school account that ever reached this
function fell through to the vague message. The brand was never missing and the
lookup never failed — it compared across two namespaces with nothing bridging
them, and null is what that returns.

WHAT WAS NOT DONE, AND WHY

Re-key the brand row to the uuid. 'org.the-academy-way' is load-bearing in five
places — jag-platform/organizations.ts, the tenant admin loader, the branding
loader twice, and BrandRegistry's own default. That fixes one lookup and breaks
the JAG command centre.

Use tenant_profiles. It is the bridge the design intended, carrying both a
synthetic organization_id and a real org_organization_id uuid. IT DOES NOT EXIST
IN PRODUCTION. It is declared in the same migration 226 that created
organization_brands, after a statement referencing org_organizations — so that
file was applied partway and stopped. Asked of the database rather than assumed:
organization_brands answers, tenant_profiles does not exist.

Building today's fix on a table that is not there would have been the third
guess of the day.

MIGRATION 356

Adds org_organization_id to the table that DOES exist, and fills it by reading
the campuses themselves rather than from a uuid typed into a file, so it cannot
drift from what the schools actually point at. Additive: nothing that reads the
synthetic key changes behaviour. A partial unique index keeps one brand per real
organization, because "which door is yours" must not be ambiguous.

THE RESOLVER

Real uuid first, registry second. The error is checked rather than the data read
blindly — before 356 that column does not exist, and PostgREST answers with an
error and a null body, the exact costume five faults in this codebase have worn.
A failure to work out the address still cannot become a failure to sign in.

TESTS

5 new, 18 on the file. The one that matters asserts the lookup happens by
org_organization_id, because both halves were always correct on their own.

STILL OPEN

Which door the leaders should actually use. The brand row claims subdomain
'academy'; theacademyway.thejag.org is what worked, showing generic "School
Platform" branding precisely because nothing resolved. Confirm against
academy.thejag.org once 356 is in.
