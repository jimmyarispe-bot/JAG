Three things Jimmy asked for in one message, and the third is the one that
mattered.

── 1. THE APPLICATION IS ACTUALLY SUBMITTED ────────────────────────────────

submitInvitedApplicationAction - /apply/start/<token>, the door every invited
family actually uses - saved the answers, wrote lead_stage =
application_submitted with a RAW UPDATE, and mailed the family the shadow-days
invitation itself. It never touched admissions_applications, never checked the
fee, never set submitted_at, and never opened a gate.

That was deliberate. Jimmy, 23 September: "once the parent completes the
application they are sent a followup email with schedule your shadow days."
Automatic, no second question - and the file said so, including the
consequence in plain words: "nobody reviews a family between application and
shadow days."

What it allowed: last night's test child read application_submitted while the
application row read in_progress with no submitted_at, and the shadow-days
invitation had already gone. A family could be invited to shadow days on an
application nobody completed and nobody paid for. Live at all five campuses.

HE REVERSED IT, 14 October: "it needs to be this way then - So the intended
order is: application completed -> the gate puts the question in front of her
-> she reads it -> she answers yes -> the family gets the booking link."

So this door now does what the portal has done since 28 September: find the
application row, run applicationFeeGate, save the answers, mark the row
submitted with submitted_at, and move the stage through transitionCaseStage -
which opens invite_to_shadow_days, whose yes branch sends the booking link.

It no longer mails shadow_days_invited itself. Sending it here would put the
link in front of a family before anybody read their application, and then send
it again when she answered yes. It sends onApplicationSubmitted instead: the
family's receipt and the leader's "an application came in".

The 23 September decision is quoted in the file above the new one, because a
diff that silently deletes "nobody reviews a family between application and
shadow days" reads like an accident. It was a decision. So is this.

── 2. THE ACCEPTANCE SCREEN STOPS PROMISING A PACKET NOBODY BUILT ──────────

applyAdmissionsDecision has always returned a warning when an acceptance
resolved no application row, or when generateEnrollmentPacket failed. Nothing
carried it anywhere: recordPostCallDecision returned {ok, action}, so the done
screen said "the enrollment packet has been built for them to sign" either way,
to the one person who could do something about it.

The warning now travels - through the action, through the redirect, onto the
page. When there is no packet the screen drops that sentence, prints the reason
in the words applyAdmissionsDecision wrote, and says the acceptance is real and
nothing needs undoing but there is nothing to sign yet.

── 3. THE DENIAL AFTER A SHADOW DAY HAS A LETTER ───────────────────────────

Deny recorded the decision and sent nothing, because buildDecisionEmail returns
null for deny - correctly, there is no inline decline letter in code and must
not be - so willEmailFamily was false and onDecisionSubmitted was never reached.

Jimmy gave the words. Asked about the one sentence that could not transfer from
his own application_declined_email - "thank you for submitting the application"
is wrong for a family who just spent two days in the building - he answered
"yes good" to "Thank you for spending the last two days with us". Asked whether
it should read "day(s)" in one row or naturally in five, he answered "read
naturally".

Migration 554: five campus rows. GA, FL and the test campus read "the last two
days"; HS and Virtual read "the day". His three remaining paragraphs are
verbatim, guarded word for word in the migration.

IT IS GATED ON A SHADOW DAY ACTUALLY HAVING HAPPENED. LEGACY_EVENT_MAP sends
every `declined` to `student_declined`, and three things produce one: this
page's Deny, the accept_or_deny gate's deny branch, and the DecisionWizard on
the decisions board. The first two only ever happen at shadow_day_completed;
the Wizard can be used at any stage. So applyAdmissionsDecision reads
admissions_shadow_days for a completed row before dispatching a denial, and
fails CLOSED - a failed read sends nothing. A letter thanking a family for two
days they never spent is exactly the failure this build exists to prevent.

The button's consequence line and the done screen both said "nothing is
emailed", which was true this morning and is not now. Both changed in this same
commit, because a consequence line that lags the behaviour by one deploy is the
same fault as item 2.
