Whether a family must answer is a decision, so it belongs on the screen

Jimmy, 27 September, looking at the live inquiry form: make ethnicity and race
required. That is a structural change, and the wording editor refuses those by
design - so the honest options were to hand-edit the definition in SQL or to
let the screen make the change. SQL was not really available either: a
version's content_hash is a sha256 of the definition as Javascript serialises
it, and a migration would have had to fake it.

REQUIRED-NESS IS THE ONE STRUCTURAL CHANGE THAT IS SAFE, and it is worth
saying why rather than treating it as a small one. A renamed key detaches
every stored answer from its question. A changed type reinterprets them. A
changed option value rewrites what an answer WAS. Requiring an answer does
none of that: it governs the next family to open the form and nothing that has
already been recorded.

So the editor gets one checkbox per question - "families must answer" - and
the guard learns to permit exactly that, only when the caller asks for it.
onlyTextChanged now takes { allowRequiredChanges }, the save path passes it,
and a required change arriving through any other caller is still refused. The
allowance is explicit at the call site rather than buried in the guard, so a
future caller with no checkbox behind it inherits the strict rule. Five more
tests, including one proving the allowance does not quietly widen to types.

The change itself is not in this commit. Ethnicity and race become required
through the screen, as a published version, the way every wording change now
happens.
