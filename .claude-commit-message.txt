the one letter that never got its button

Jimmy, 12 October, on the test campus's first staff alert: "bad news: no
button in the email."

He was right, and this is the second time the same template has been the
exception. On 10 October he asked for "an actual button that will go into
these emails with the links tied to them", and the commit that answered him
was titled "every link in every letter is a button now". It was not true.

Eighty-four of the eighty-five active templates are plain text, and those got
buttons. inquiry_staff_alert is the eighty-fifth, written in HTML. On 10
October its markup was escaped and reached Danni's inbox as view-source. The
fix for that passed the markup through untouched - and DELIBERATELY SKIPPED
THE BUTTON, on my reasoning that "a link somebody wrote an anchor around is a
decision already taken."

That is a reasonable rule about markup and the wrong answer to what Jimmy
asked. He did not ask for buttons only where the author forgot to write one.
He asked for buttons. So the call to action in that letter arrived as a bare
underlined link, two days later, in a test built to catch exactly this.

WHAT CHANGES

An anchor ALONE IN ITS OWN PARAGRAPH now becomes a button in the already-HTML
path too - the same decision renderBlock already makes for a bare URL alone on
its line. An anchor with words around it stays a link, because a button in the
middle of a sentence is not a button. inquiry_staff_alert shows both shapes in
one letter, which is why the distinction has to hold:

  <p>Email: <a href="mailto:...">...</a><br>Phone: <a href="tel:...">...</a></p>
  <p><a href="{{interest_link_action}}">Send them the interest meeting link</a></p>

The first stays. The second becomes the button. The mailto: and tel: links are
refused by the http/https check as well, which is what should be true of a
rule worth keeping.

buttonBlock is split into buttonBlockRaw, which touches nothing it is handed,
because the two callers escape at different moments - the plain-text path
escapes at the button, the HTML path escaped when it substituted the merge
field. Escaping twice is how a URL with an & in it becomes a dead link, and
nobody notices that before a parent clicks.

THE REAL REASON ONE TEMPLATE WAS WRONG TWICE

letter-html.ts had NO TESTS AT ALL. Eighty-four letters were right and the
eighty-fifth was broken twice, in two different ways, with nothing watching.

tests/unit/communications/letter-html-buttons.test.ts now exists: 16
assertions built from that template's stored body and the exact values from
the letter Jimmy screenshotted, including both old failures as regressions -
no escaped markup in view-source, and no empty href left behind.

Checked, not assumed:

  - scoped typecheck of the module and the new test, exit code read straight
    off tsc with no pipe: clean
  - all 16 assertions executed against the built module: one purple button
    with white lettering, label taken from the anchor's own words, href is
    the send-interest-link address, naked URL still printed underneath,
    EXACTLY ONE button from three anchors, mailto: and tel: untouched,
    javascript: refused, an anchor with no words gets no button, the plain
    text path still produces "Choose your time", and an &amp; is not escaped
    twice
  - one query over all 101 template rows - `where body ~* '<[a-z][^>]*>'` -
    confirms inquiry_staff_alert is still the only one written in HTML, so
    this covers the whole estate rather than the one letter I happened to
    look at. That is the query I should have run on 10 October instead of
    generalising from three plain-text templates.
