Jimmy booked an interest call with Danni for 7:00pm at 6:36pm as a test,
and asked at 7:13 why she had no notes email.

── WHAT WAS NOT WRONG ──────────────────────────────────────────────────────

A dry run of the discovery pass answered most of it. Google is reachable,
the token is good, all four calendars are read INCLUDING Danni's,
calendarProblems empty, campusesWithNoCalendar empty, 210 bookings seen.
The lead existed with his address on it, created 6:23pm, inside the
90-day window; 337 leads considered, which is all of them. The queue is
draining — 13 letters went out at 6:24pm, one minute after the test
inquiry.

── WHAT I GOT WRONG, AND CORRECTED BEFORE WRITING ANY CODE ─────────────────

I told him the letter was being suppressed because the meeting had
already started, and proposed a grace window. That was wrong. The
post-call letter is ALREADY queued for a meeting in the past, on purpose,
and the comment above it says why: the family's confirmation is worthless
six weeks late, but "what happened and what should happen next" is
exactly as useful late, because the decision it asks for has not been
made. `if (alreadyHappened) continue` sits BELOW that block, not above
it. I would have shipped a fix for a bug that does not exist.

── WHAT IS ACTUALLY UNEXPLAINED ────────────────────────────────────────────

The booking was never matched. Every silent exit in that loop was checked
against the database and none applies: no admissions_interviews row, no
admissions_tours row, stage is new_inquiry so the tour branch is not
taken, bookedAt empty. matchBookingToLead reads event.attendees[].email
and nothing else, so the remaining explanation is that his address is not
a guest on that event — Google's appointment schedules put the booker in
the notification body, which the matcher never reads.

NOT FIXED HERE. Widening the matcher to read the booker out of the
description is a real change to how a family is identified, and it waits
until somebody has looked at the actual guest list on that event.

── WHAT THIS COMMIT DOES ───────────────────────────────────────────────────

  "2. run every 2 minutes"

booking-scan moves from hourly to every two minutes. It reads calendars,
records bookings and queues the notes letter; it writes no chase letters
and takes no night claim, so the frequency costs little. With the
five-minute drain behind it the worst case is about seven minutes from
booking to inbox, against sixty before.

The hourly pass was built on 5 October against "usually not before 3
hours" of notice. Twenty-four minutes defeats it.
